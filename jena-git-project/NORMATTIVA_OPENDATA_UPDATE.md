# Normattiva OpenData Update Routine

This document explains the lightweight Normattiva update routine used by the demo application.

## Why This Exists

The previous update idea scraped the Normattiva public homepage and tried to infer legal relations from nearby links. That was weak because:

- the homepage is not a stable data API,
- page layout changes can break the parser,
- nearby links are not enough evidence for reliable legal relation extraction,
- relation RDF should not be generated by guessing.

The current routine is intentionally narrower and more defensible.

It uses the official Normattiva OpenData API endpoint described in the OpenAPI documentation:

```text
POST /api/v1/ricerca/aggiornati
```

The official request body schema is:

```json
{
  "dataInizioAggiornamento": "date-time",
  "dataFineAggiornamento": "date-time"
}
```

The endpoint returns acts updated between two dates.

The next official endpoint used by the code foundation is:

```text
POST /api/v1/atto/dettaglio-atto
```

The request uses candidate metadata from the update response:

```json
{
  "dataGU": "string",
  "codiceRedazionale": "string"
}
```

The response contains an `atto` object with fields such as title, act type, act date, publication date, vigency dates, text state, and article HTML.

## Current Implementation

Main class:

```text
src/main/java/it/legislation/crawler/NormattivaUpdateRunner.java
```

Default API base:

```text
https://api.normattiva.it/t/normattiva.api
```

Default endpoint built by the runner:

```text
https://api.normattiva.it/t/normattiva.api/api/v1/ricerca/aggiornati
```

Default output:

```text
data/clean/normattiva_updates.tsv
```

The TSV contains update candidates with fields such as:

```text
codice_redazionale
data_gu
denominazione_atto
numero_atto
titolo_atto
data_emanazione
data_ultima_modifica
ultimi_atti_modificanti
endpoint
fetched_at
```

The runner also contains small helper methods for the future detail stage:

```text
actDetailEndpoint(...)
actDetailRequestBody(...)
fetchActDetails(...)
parseActDetails(...)
```

These helpers fetch and parse act detail responses. They do not write RDF.

The detail stage can be run explicitly after update discovery:

```bash
mvn -B exec:java -Dexec.mainClass=it.legislation.crawler.NormattivaUpdateRunner -Dexec.args=details
```

Default detail output:

```text
data/clean/normattiva_details.tsv
```

The detail TSV can be inspected through the local API:

```text
GET /api/normattiva/details?limit=50
```

The frontend shows these rows in the Normattiva tab as **Detail evidence**. They remain separate from the RDF relationship table.

Optional configuration:

```text
NORMATTIVA_DETAILS_OUTPUT
NORMATTIVA_DETAILS_LIMIT
```

The detail TSV stores the candidate metadata beside the structured fields returned by the official detail API. It is a cache/staging file for inspection and later relation validation.

## Configuration

The update interval can be controlled with environment variables:

```text
NORMATTIVA_UPDATE_START
NORMATTIVA_UPDATE_END
NORMATTIVA_UPDATE_LOOKBACK_DAYS
```

Examples:

```bash
NORMATTIVA_UPDATE_START=2026-08-01T00:00:00Z
NORMATTIVA_UPDATE_END=2026-08-02T00:00:00Z
mvn -B exec:java -Dexec.mainClass=it.legislation.crawler.NormattivaUpdateRunner
```

If no explicit dates are provided, the runner uses a small rolling lookback window.

## Important Design Choice

The routine currently discovers updated acts.

It does not automatically create legal-relation RDF from the update response.

Reason:

- The `aggiornati` endpoint tells us which acts changed.
- It does not, by itself, provide enough structured evidence to safely emit `ilg:modifies`, `ilg:modifiedBy`, `eli:commences`, or `eli:commenced_by`.
- Relation extraction should use a later detail endpoint or downloaded OpenData files where the modifying and modified acts are explicit.

This is why the runner leaves existing relation RDF untouched.

## How This Answers The Feedback

The professor suggested the newer Normattiva OpenData APIs and specifically mentioned:

```text
/api/v1/ricerca/aggiornati
```

The current implementation follows that direction:

- it uses the official update-search API shape,
- it stores update candidates instead of losing them between runs,
- it avoids hallucinated relation generation,
- it keeps the implementation small and testable,
- it creates a foundation for the next robust step: fetching details for each updated act.

The detail helper follows the same principle. It reads structured `AttoDto` fields from the official detail response, but it still does not claim a legal relation unless a later step can identify explicit relation evidence.

## Tests

Covered by:

```text
src/test/java/it/legislation/crawler/NormattivaUpdateRunnerTest.java
```

Current tests verify:

- the endpoint path is built correctly,
- the official request body fields are used,
- `listaAtti` JSON responses are parsed,
- the official detail endpoint and request body are built correctly,
- detail `atto` responses are parsed,
- detail fetch uses the official endpoint without writing RDF,
- update candidates can be read back from TSV,
- detail rows can be fetched and written to a separate TSV,
- detail rows can be served back through the web API,
- detail evidence can be shown in the UI without mixing it with RDF relations,
- update candidates are written to TSV,
- relation RDF is not generated when the API response does not contain relation evidence.

## Next Step

The next routine should process each fetched detail and identify explicit evidence for:

```text
updated act
modifying act
modified act
relation type
version/expression affected
```

Only after that step should the pipeline emit automatic Normattiva relation RDF.
